    Consistencia Semántica y Etiquetado de Tópicos con un LLM¶

    Python + Hugging Face¶

    En la unidad anterior (5a) estimamos tres modelos LDA sobre el corpus de críticas de películas, con $k=12$, $k=20$ y $k=25$ tópicos, y exportamos las 15 palabras más representativas de cada tópico a tres archivos CSV.

    En este notebook usaremos un LLM de código abierto (vía Hugging Face transformers) para dos tareas complementarias a lo que ya hicimos en R:

    1. Etiquetar cada tópico con un nombre corto y descriptivo, a partir de sus palabras clave.
    2. Evaluar la consistencia semántica (topic coherence) de cada tópico: ¿forman estas palabras un tema reconocible, o son una mezcla poco relacionada?

    Esto nos da una segunda fuente de evidencia — cualitativa y semántica — para comparar los tres valores de $k$, complementando las métricas estadísticas ya vistas (perplexity, elbow method).

    🖥️ Antes de ejecutar: revisa tu hardware

    Este notebook detecta automáticamente el hardware disponible y usa la configuración más rápida para cada caso — no necesitas cambiar nada en el código.

    • Google Colab con GPU activada, o Mac con Apple Silicon (M1/M2/M3/M4): debería tardar solo un par de minutos en total.
    • Sin GPU (por ejemplo, Mac con chip Intel, o un PC sin GPU NVIDIA): el notebook lo detecta e imprime una advertencia (⚠️ No se detectó GPU...) antes de cargar el modelo, y luego corre en CPU — esto puede tomar decenas de minutos. Si ves esa advertencia y la celda de evaluación es muy lenta, cambia a Google Colab y activa GPU en Entorno de ejecución > Cambiar tipo de entorno de ejecución > GPU (T4).
    • Si el notebook corre lento sin mostrar esa advertencia, algo no está funcionando como se espera — avísale a tu profesor antes de esperar a que termine.

    🎯 ¿Que queremos lograr?¶

    • Cargar un modelo instruccional open-source desde Hugging Face y ejecutarlo localmente o en Colab.
    • Diseñar un prompt que le pida al LLM una salida en un formato específico y parseable.
    • Aplicar el LLM sistemáticamente a los tópicos de los tres modelos ($k=12,20,25$).
    • Comparar la coherencia semántica promedio entre valores de $k$ como evidencia adicional para elegir el número de tópicos.

    📝 Nota: El término parseable (o parsable) se refiere a cualquier texto, dato o código que posee una estructura clara y predecible, permitiendo que otro programa pueda analizarlo automáticamente, descomponerlo y extraer información sin intervención humana.

    🤖 ¿Qué modelo usamos?¶

    Usaremos Qwen/Qwen2.5-3B-Instruct.

    Es una alternativa a modelos como meta-llama/Meta-Llama-3-8B-Instruct con ventajas prácticas para este notebook:

    • No requiere acceso restringido ("gated"): los pesos de Llama-3 en Hugging Face exigen aceptar una licencia y solicitar acceso (con aprobación no inmediata) antes de poder descargarlos, lo que agrega fricción a un ejercicio de curso. Qwen2.5 se descarga directamente.
    • Tamaño acotado (3B): para una tarea estructurada y acotada como esta (leer 15 palabras, producir una etiqueta y un puntaje), no se necesita un modelo de 7-8B parámetros. Un modelo más pequeño se descarga y carga notablemente más rápido, lo cual importa especialmente en Colab, donde la caché no persiste entre sesiones (ver nota en la siguiente celda).

    📌 El nombre del modelo está aislado en una sola variable (MODEL_NAME). Si prefieres más calidad a cambio de una carga más lenta, puedes cambiarla por "Qwen/Qwen2.5-7B-Instruct" o, si ya tienes acceso aprobado y un token de Hugging Face configurado, "meta-llama/Meta-Llama-3-8B-Instruct" — el resto del notebook funciona igual.

    ⚠️ Sobre el hardware: ver la nota al inicio del notebook y la explicación en la sección "Cargar el modelo" — el código detecta automáticamente si usar CUDA, Apple Silicon (MPS) o CPU.

    🧠 I. Cargar el modelo¶

    Detectamos automáticamente el tipo de GPU disponible y cargamos el modelo de la forma más adecuada para cada caso: CUDA (con cuantización en 4 bits), Apple Silicon (MPS, sin cuantizar) o CPU como último recurso.

    ⚠️ bitsandbytes (cuantización en 4 bits) solo funciona con GPUs NVIDIA (CUDA) — por ejemplo, la GPU T4 gratuita de Google Colab. No funciona en Mac (Apple Silicon ni Intel), y si el código intenta usarlo de todas formas, device_map="auto" puede terminar ejecutando el modelo silenciosamente en CPU, lo cual es extremadamente lento para un modelo de 3B (decenas de minutos para las 57 llamadas de las secciones siguientes) — sin ningún error o advertencia visible que lo indique.

    Por eso esta celda revisa explícitamente qué hardware hay disponible:

    • CUDA disponible (Colab, PC con GPU NVIDIA): cuantizamos en 4 bits con bitsandbytes.
    • MPS disponible (Mac con chip Apple Silicon: M1, M2, M3, M4): cargamos el modelo en float16 directamente sobre la GPU integrada de Apple, sin bitsandbytes. Un modelo de 3B en float16 ocupa ~6 GB, lo que cabe cómodamente en la memoria unificada de un Mac moderno.
    • Ninguna de las anteriores: el modelo corre en CPU. Si ves este mensaje y la celda de evaluación demora demasiado, considera ejecutar el notebook en Google Colab.

La primera vez (o en cada sesión nueva de Colab, donde la caché no persiste), Hugging Face debe descargar los pesos del modelo — con Qwen/Qwen2.5-3B-Instruct esto son unos ~6 GB, notablemente menos que los ~15 GB de una variante de 7B.     🛑 Definiendo los tokens de parada (stop_token_ids)¶

    Por defecto, generate() solo se detiene cuando produce el eos_token_id del modelo. El problema es que Qwen2.5-Instruct señala el fin de un turno de conversación con un token especial adicional, <|im_end|>, que no siempre coincide con el eos_token_id por defecto del tokenizer.

    Si no le indicamos explícitamente este token como una señal de parada válida, generate() puede no reconocer el final natural de la respuesta y seguir generando texto de relleno hasta agotar max_new_tokens — algo especialmente costoso aquí, ya que este proceso se repite en 57 llamadas al modelo.

    El código:

    1. Obtiene el ID numérico del token <|im_end|> mediante tokenizer.convert_tokens_to_ids().
    2. Construye stop_token_ids, comenzando con el eos_token_id por defecto del modelo.
    3. Si <|im_end|> existe en el vocabulario del tokenizer (es decir, no es un token desconocido, unk_token_id), lo agrega también a la lista.

    El resultado, stop_token_ids, se pasa luego a model.generate() como eos_token_id, permitiendo que la generación se detenga correctamente en cualquiera de los dos tokens de fin de turno.

    🤖 La función query_llm()¶

    Esta función encapsula todo el proceso de enviarle un prompt al modelo y recuperar únicamente el texto que generó como respuesta.

    1. Construcción del mensaje. El prompt se envuelve en el formato de mensajes de chat ({"role": "user", "content": prompt}) que espera un modelo instruct.

    2. Aplicación de la plantilla de chat. tokenizer.apply_chat_template() convierte ese mensaje en la secuencia de tokens con el formato específico que Qwen2.5-Instruct espera (incluyendo marcadores especiales de rol y turno), y add_generation_prompt=True agrega además la señal que le indica al modelo que debe comenzar a generar su respuesta. El resultado se mueve al mismo dispositivo (model.device) donde vive el modelo — CPU o GPU.

    3. Generación. model.generate() produce la respuesta:

      • max_new_tokens limita cuántos tokens nuevos puede generar como máximo (por defecto, 80).
      • do_sample=False hace que la generación sea determinista (siempre elige el token más probable), en vez de introducir aleatoriedad.
      • eos_token_id=stop_token_ids usa la lista de tokens de parada definida en la celda anterior, para que el modelo se detenga correctamente al terminar su turno.
      • pad_token_id evita advertencias relacionadas con el token de relleno.

    4. Decodificación. output[0][input_ids.shape[-1]:] descarta los tokens del prompt original y conserva solo los tokens generados como respuesta. tokenizer.decode(..., skip_special_tokens=True) los convierte de vuelta a texto legible, eliminando tokens especiales como <|im_end|>. Finalmente, .strip() elimina espacios en blanco sobrantes al inicio o final.

    El resultado es una función reutilizable: basta con llamar query_llm("mi pregunta") para obtener la respuesta del modelo como una cadena de texto lista para usar.

    def query_llm(prompt, max_new_tokens=80):
    """Envía un prompt al modelo usando su plantilla de chat y devuelve solo el texto generado."""
    messages = [{"role": "user", "content": prompt}]
    inputs = tokenizer.apply_chat_template(
        messages, add_generation_prompt=True, return_tensors="pt", return_dict=True
    ).to(model.device)

    output = model.generate(
        **inputs,
        max_new_tokens=max_new_tokens,
        do_sample=False,
        eos_token_id=stop_token_ids,
        pad_token_id=tokenizer.pad_token_id,
    )

    respuesta = tokenizer.decode(output[0][inputs["input_ids"].shape[-1]:], skip_special_tokens=True)
    return respuesta.strip()

    ✂️ Palabras clave por tópico¶

    A continuación, creamos una función simple para obtener, dado un tópico, sus $n$ palabras con mayor probabilidad ($\beta$). Recordemos: $\beta$ es la distribución tópico → palabra de LDA — para un tópico dado, qué tan probable es que aparezca cada palabra del vocabulario. Una $\beta$ alta para una palabra dentro de un tópico indica que esa palabra es muy característica de ese tópico (a diferencia de $\gamma$, que es la distribución documento → tópico, usada en la Unidad 5a para ver qué tópicos predominan en cada documento).

    El CSV exportado desde R ya viene ordenado por $\beta$ descendente dentro de cada tópico (por el arrange(topic, -beta) de la Unidad 5a), pero igual ordenamos explícitamente aquí en Python — así la función es correcta sin depender de que ese orden se mantenga (por ejemplo, si el CSV se regenera de otra forma, o el dataframe se filtra o combina con otros antes de llegar aquí).

    def get_topic_words(df, topic_id, n=15):
    palabras = (
        df[df["topic"] == topic_id]
        .sort_values("beta", ascending=False)
        .head(n)["term"]
        .tolist()
    )
    return palabras

    🎲 ¿Cómo "decide" el modelo ese número entre 1 y 5?¶

    Un LLM genera texto token por token, prediciendo en cada paso "¿cuál es el siguiente token más probable?", dado todo el contexto anterior. Cuando llega al punto donde debe escribir el número después de "Coherencia (1-5): ", el modelo:

    1. Calcula una distribución de probabilidad sobre todos los tokens posibles de su vocabulario para esa posición.
    2. Dado ese contexto específico, tokens como 1, 2, 3, 4, 5 tienen probabilidades mucho más altas que cualquier otra palabra — porque el modelo aprendió durante su entrenamiento, a partir de enormes cantidades de texto (incluyendo tareas de calificación y evaluación de similitud semántica), qué continuaciones son razonables en ese tipo de contexto.
    3. Cuál de esos candidatos elige depende de qué tan coherentes le "parecen" las palabras del prompt, según los patrones que absorbió durante el entrenamiento — no de un cálculo explícito sobre esas palabras.
    4. Como usamos do_sample=False en model.generate(), la generación es determinista (greedy): en cada paso el modelo elige el token de mayor probabilidad, sin aleatoriedad. El mismo prompt siempre produce la misma respuesta.

    📌 Idea clave: el número no es el resultado de un algoritmo que "compara" las palabras entre sí — es una predicción estadística aprendida, la misma mecánica con la que el modelo genera cualquier otra palabra del texto. Aquí simplemente el contexto (las instrucciones del prompt) empuja la probabilidad hacia los dígitos 1-5 en esa posición específica.

    ⚖️ Diferencia explícita con la Unidad 5c (Embeddings)¶

    Este notebook (5b, LLM) Unidad 5c (Embeddings)
    ¿Qué mide? Le pide al LLM que opine un número 1-5 Calcula la similitud coseno promedio entre los vectores de las palabras
    ¿Hay una fórmula? No — es texto generado, token por token Sí — un valor numérico derivado directamente de los embeddings
    ¿De dónde sale el resultado? De qué token es más probable, según patrones aprendidos en el entrenamiento De una operación matemática (distancia/similitud) sobre vectores
    ¿Es reproducible con otro modelo? Puede variar según el LLM usado El resultado depende del modelo de embeddings, pero el cálculo en sí es determinista y transparente

    Son dos formas fundamentalmente distintas de resolver el mismo problema: 5b delega el juicio de coherencia en el criterio (implícito, aprendido) de un LLM; 5c lo reemplaza por una medida matemática explícita y verificable.

    🔎 parse_response(): extrayendo la respuesta estructurada del LLM, el puntaje y la justificación de la respuesta¶

    Esta función usa expresiones regulares para extraer tres campos desde el texto libre que devuelve el LLM: la etiqueta del tópico, su coherencia (1-5) y la justificación.

    El detalle no trivial está en la regex de coherencia: se usa [^:]* (cualquier cosa que no sea :) entre la palabra "Coherencia" y los dos puntos, en vez de capturar el primer dígito que aparezca. Esto es necesario porque el propio prompt que le enviamos al modelo ya contiene un dígito dentro de un paréntesis — "Coherencia (1-5): ..." — y una regex más ingenua podría capturar por error el "1" de "(1-5)" en lugar del número real que el modelo respondió después de los dos puntos. Como "(1-5)" no contiene :, [^:]* lo deja pasar sin detenerse ahí, y solo el dígito que sigue al : real queda capturado.

    Además, cada regex usa [Ee]/[Cc]/[Jj] para tolerar mayúsculas o minúsculas en la etiqueta, y \** para ignorar posibles asteriscos de negrita en markdown que el modelo a veces agrega alrededor de la etiqueta o el número.

    Si algún campo no aparece en la respuesta (el .search() no encuentra coincidencia), se devuelve None en su lugar — así el resto del código puede detectar respuestas incompletas o mal formateadas sin que el programa falle.

def evaluate_model_topics(df, k, n_words=15, pbar=None):
    resultados = []
    for topic_id in sorted(df["topic"].unique()):
        palabras = get_topic_words(df, topic_id, n=n_words)
        prompt = build_prompt(palabras)
        respuesta = query_llm(prompt)
        parsed = parse_response(respuesta)
        parsed.update({"k": k, "topic": topic_id, "palabras": ", ".join(palabras)})
        resultados.append(parsed)
        if pbar is not None:
            pbar.update(1)

    return pd.DataFrame(resultados)

    ⚠️ Una limitación real: los puntajes se concentran en 5¶

    Si observas la distribución completa de coherencia (no solo el promedio), vas a notar algo importante: la gran mayoría de los tópicos reciben un puntaje de 5, y muy pocos reciben 4, 3 o menos — independientemente del valor de $k$.

    Esto no es un error de parseo (ya verificamos que el formato se extrae correctamente); es una limitación real de usar un modelo de 3B para autoevaluarse con una escala numérica: tiende a ser poco discriminante y a concentrar sus respuestas cerca del extremo superior de la escala, en lugar de repartirlas según la calidad real de cada tópico.

    ¿Por qué importa esto? Porque si casi todos los tópicos obtienen 5, el promedio por valor de $k$ pierde buena parte de su capacidad para diferenciar entre modelos — la comparación entre $k=12$, $k=20$ y $k=25$ termina siendo mucho menos informativa de lo que sería con puntajes mejor distribuidos.

    📌 Idea clave: esta es una limitación genuina del enfoque LLM, no un defecto del ejercicio — y es exactamente el tipo de comparación crítica entre métodos tradicionales y LLM que buscamos hacer en este curso. Las métricas estadísticas de la Unidad 5a (perplexity, el método del codo) no tienen este problema de "techo": producen valores continuos que sí distinguen claramente entre distintos $k$. Un modelo más grande (7B o superior), o un prompt que pida una justificación antes del puntaje (para forzar un razonamiento más cuidadoso), probablemente reduciría este efecto — quedan como posibles extensiones de este ejercicio.

    ✅ ¿Qué concluimos?¶

    Este notebook agrega una evidencia cualitativa y semántica a la selección de $k$, complementando las métricas puramente estadísticas de la Unidad 5a:

    • R / Quanteda + topicmodels: produce los tópicos y las métricas de ajuste (perplexity) de forma reproducible y computacionalmente eficiente.
    • Python + LLM: interpreta el contenido de esos tópicos — algo que ninguna métrica estadística puede hacer por sí sola — y propone etiquetas listas para presentar a una audiencia no técnica.

    📌 Idea clave: ni el enfoque estadístico ni el LLM son suficientes por separado para elegir y comunicar un buen modelo de tópicos — la combinación de ambos es lo que da una respuesta completa.
